🧨 Blast Radius

Impact-aware pull-request review, built on Entire Graph. It shows what a change really touches, whether it drifted from the ask, and the smallest test set that actually covers it — before anyone hits merge.

↓ Space next · ↑ back github.com/entire-hackathon/blast-radius

Every pull request

Three things go unseen on every PR.

01 The reviewer can't see the blast radius. A three-line change to a shared helper can ripple through twenty call sites and three services. The diff shows the three lines. The review happens on vibes.
02 CI runs everything. No signal about which tests exercise the change, so the whole suite runs on every push — slow feedback, wasted minutes, and still no proof the right paths were covered.
03 The change quietly grew. The ticket said “add rate limiting to one endpoint.” The PR also re-signatured a database method. Nobody flagged it, because nobody cross-checked the diff against the original ask.

What it doesBlast Radius

Graph as a dependency, not a viewer

Four graph queries, joined into one decision.

diff
changed symbols, each with a heuristic dependent count
impact
per symbol: callers, callees, type consumers, data flows, co-change files, siblings
neighbors
distance refinement for ranking the tests
checkpoint
resolves the change back to the session that produced it
How it uses the graphBlast Radius

Connecting graph findings with checkpoint intent

The graph says what changed. The checkpoint says what was asked.

For each changed symbol, the tool measures lexical overlap between its name and the intent's keywords, and reads how many things depend on it.

Low overlap + real dependents → flagged as scope drift, with the graph path as evidence.

outside intent wide-reaching covered

Raw impact output alone isn't enough — the brief says so. This cross-check is the part that clears that bar.

The novel partBlast Radius

Evidence, not assertions

Every flag links to the graph path that justifies it.

# why Database.query is flagged
intent (checkpoint-trailer): "Rate-limit the redirect endpoint"
changed here — signature changed, 6 dependents — src/db/database.ts:12
reaches LinkRepo.byId → RedirectService.resolve
        └─ none of this is named in the ticket

Machine-readable

SARIF to the Code scanning tab, full JSON for agents — the complete node list, not just counts.

Honest about limits

A static call graph: precise for direct calls, conservative on dynamic dispatch — the same tradeoff every “find usages” makes. So it shows the path, and the reviewer verifies.

VerifiableBlast Radius

Works today, on any repo

One workflow file. No account. No config.

# .github/workflows/blast-radius.yml
on: pull_request
jobs:
  blast-radius:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: entire-hackathon/blast-radius@v0.1.0

Intent, tiered

PR description and linked issue out of the box. Sharper when the team uses Entire — the actual captured agent prompt, no extra work.

Degrades gracefully

Offline fixture mode runs the whole pipeline with only Node. Comment blocked by permissions? It writes the report to the job summary instead.

Language coverage

Go, TypeScript, JavaScript, Python and 30+ more — whatever entire-graph parses semantically.
